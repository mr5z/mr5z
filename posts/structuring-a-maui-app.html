Structuring a .NET MAUI App with MvvmEssentials

Nov 1, 2026 · Intermediate
maui mvvm architecture

In the last post I toured a small demo app built with MvvmEssentials. Demos are easy to keep tidy. This post is about the opposite: Reaps, a workout tracker I'm building, with around 50 screens, a free part, a paid part, and an AI coach. These are the habits that kept it from turning into a mess.

Quick refresher on the words I'll use:

  • Page: what the user sees (the XAML).
  • View model: the plain C# class behind a page. It holds the data the page shows and the actions its buttons run. It never touches buttons or colors directly.
  • MvvmEssentials: the library that connects the two, moves between pages, and tells each view model when things happen ("you're on screen now", "you're gone now").

1. One list of every screen

Every page and its view model are paired once, at startup, in one place. If you want to know what screens the app has, you read one file:

registry
    .MapPage<TemplatesPage, TemplatesViewModel>()
    .MapPage<SessionDetailPage, SessionDetailViewModel>()
    .MapPage<SettingsPage, SettingsViewModel>();

// Popups: same thing, they just hand a result back.
registry
    .MapPage<ExercisePickerPopup, ExercisePickerViewModel>()
    .MapPage<ChoiceSheetPopup, ChoiceSheetViewModel>();

// Wizard steps: views that live inside one page.
registry
    .MapPage<OnboardingHostPage, OnboardingHostViewModel>()
    .MapView<OnboardingGoalView, OnboardingGoalViewModel>()
    .MapView<OnboardingScheduleView, OnboardingScheduleViewModel>();

Group them with a short comment per group ("Setup", "Popups", "Coach"). It reads like a table of contents.

2. Layers: build it like floors of a house

The app is split into projects, stacked like floors. Each floor may use the floors below it, never the ones above:

Reaps            the app itself: XAML pages, icons, phone-specific code
  ↑
Reaps.Pro        paid features (AI coach, cloud backup)
  ↑
Reaps.Suggestions  optional smart tips on top of the logbook
  ↑
Reaps.Logbook    the free workout logbook: its screens and view models
  ↑
Reaps.Data       the database and the server client
  ↑
Reaps.Domain     the basics: models, text, small helpers

Two things fall out of this for free:

  • The free app can't accidentally depend on the paid one. Reaps.Logbook simply has no reference to Reaps.Pro, so the compiler refuses. No code review needed to catch it.
  • View models don't need MAUI. Only the top floor knows it's a phone app. Every view model lives in a plain .NET library, which means its tests run on any machine, in seconds, without an emulator.
That second point is the big one. MvvmEssentials' view model base classes don't drag in the UI framework, so you can put them in a plain class library. Do it from day one; moving them later is painful.

3. Folders by feature, not by kind

The usual starter template gives you Views/, ViewModels/, Services/. That works for 5 screens. At 50, "where's the stuff for Home?" means opening three folders.

Instead, each feature gets a folder, and everything about it lives there:

Reaps.Logbook/
  Home/
    ViewModels/HomeViewModel.cs
    Sections/WeekCardSection.cs
    Sections/GoalCardSection.cs
    IHomePrompts.cs
  Workout/
    ViewModels/ActiveWorkoutViewModel.cs
    Sections/RestBarSection.cs
  Templates/
  History/
  ...

Code that no single feature owns goes in a small number of shared folders (Models, Services, Text). If something is used by many features but clearly belongs to one, it stays in that one.

4. Plugs: how a lower floor shows things from a higher floor

Here's a puzzle the layers create. The Home screen lives in the free logbook. But the paid and "Suggestions" features want to put a few things on Home: a sparkle button, a Monday check-in chip. Home isn't allowed to know those features exist.

The answer is a plug (an interface). Home says "I have a slot here, and whatever fills it must look like this":

// In Reaps.Logbook: the free app defines the slot.
internal interface IHomePrompts : INotifyPropertyChanged
{
    bool HasCheckIn { get; }
    IAsyncRelayCommand OpenCheckInCommand { get; }

    void Show(IReadOnlyList<WorkoutSession> sessions, bool hasActiveWorkout);
}

The higher floor fills it:

// In Reaps.Suggestions: the optional feature plugs in.
internal sealed partial class SuggestionsPromptsSection(...)
    : SectionViewModel, IHomePrompts
{
    ...
}

// At startup, in the app:
builder.Services.AddScoped<IHomePrompts, SuggestionsPromptsSection>();

Home just asks for an IHomePrompts and binds to it. It never learns who's behind it. Rip out Suggestions, plug in an empty version, and Home still works.

5. SectionViewModel: stop writing giant view models

This is the part I'm happiest with.

A busy screen like Home has a lot going on: a "start workout" card, a "this week" card with a progress ring, a goal card, tips. If all of that goes into HomeViewModel, you get a 2,000-line file with 20 dependencies that nobody wants to touch.

A section is a small view model for one part of a page. Home's "This week" card is WeekCardSection. It has its own properties and its own dependencies, and that's all it knows about:

internal sealed partial class WeekCardSection(ISettingsStore settings, IWording wording)
    : SectionViewModel
{
    public int WorkoutsThisWeek { get; private set; }
    public int WeeklyTarget { get; private set; }
    public double WeekFraction { get; private set; }

    public void Show(HomeSummary summary, WeightUnit unit)
    {
        WorkoutsThisWeek = summary.WorkoutsThisWeek;
        WeeklyTarget = _settings.DaysPerWeek;
        WeekFraction = WeeklyTarget <= 0 ? 0 : WorkoutsThisWeek / (double)WeeklyTarget;
        ...
    }
}

The page's view model just takes it in and exposes it:

internal sealed partial class HomeViewModel(..., WeekCardSection weekCard, GoalCardSection goalCard)
    : TabViewModel
{
    public WeekCardSection WeekCard { get; } = weekCard;
    public GoalCardSection GoalCard { get; } = goalCard;
}

And the XAML reaches into it with a dot:

<Label Text="{Binding WeekCard.StreakWeeks}" />
<charts:RingDrawable Fraction="{Binding WeekCard.WeekFraction}" />

Why not just a plain class?

You could split things into plain classes yourself. What SectionViewModel adds is that it lives and dies with its page. You register it once:

registry
    .RegisterSection<WeekCardSection>()
    .RegisterSection<RestBarSection>();

Each page that asks for one gets its own fresh copy, and when the page goes away, so does the section. If the section started something that needs stopping, it says so in OnDispose. The rest timer bar on the workout screen ticks four times a second; when you leave the screen, it cleans up after itself:

internal sealed partial class RestBarSection(...) : SectionViewModel
{
    protected override void OnDispose()
    {
        if (_ticker is null)
            return;

        _ticker.Tick -= HandleTick;
        _ticker.Stop();
        _ticker = null;
    }
}

No forgotten timers ticking in the background on a screen nobody can see.

Sections are easy to test

A section is small, and it doesn't need MAUI (see the layers above), so testing it is just "make one, call it, check it":

[Fact]
public void Show_FillsTheRingAgainstTheDaysPerWeek()
{
    _settings.DaysPerWeek = 4;

    _card.Show(Summary(workouts: 3), WeightUnit.Kilograms);

    Assert.Equal(0.75, _card.WeekFraction);
}

6. Read everything first, then show it all at once

A small trick that made the app feel much smoother.

Each time your code waits for something (await), the screen gets a chance to redraw. So if you load one card, set its values, load the next card, set its values, the user sees the page fill in piece by piece, cards jumping as others arrive.

The fix is a simple rule: a section that loads data has two methods.

  • LoadAsync reads the data and returns it. It changes nothing on screen.
  • Show puts it on screen. It never waits for anything.

The page loads every section first, then shows them all in a row:

private async Task ReloadAsync()
{
    // 1. Read. Nothing on screen changes yet.
    var summary = await _stats.GetHomeSummaryAsync();
    var goalCard = await GoalCard.LoadAsync(hasNoHistory, unit);
    var hintCard = await HintCard.LoadAsync(next, sessions);

    // 2. Show. No awaits from here on, so Home changes in one frame.
    WeekCard.Show(summary, unit);
    GoalCard.Show(goalCard);
    HintCard.Show(hintCard);
}

The whole page changes in one go. No flicker, no jumping. A section that only shows what the page already read (like the week card) just has Show.

7. Smaller things worth copying

Pass data between pages with real types, not strings. Mark a property as a parameter and you get a typed With(...) to call. Typos become compile errors:

[NavigationParameter]
public Guid TemplateId { get; set; }

// Somewhere else:
await _navigation.NavigateAsync(TemplateDetailViewModel.With(templateId: template.Id));

Popups return an answer. Opening a picker reads like calling a method. No shared variables, no events to listen to:

var result = await _popups.PresentAsync<ExercisePickerViewModel, ExercisePickerResult>();
if (!result.TryGetValue(out var picked) || picked.Selected is null)
    return; // the user closed it without picking

AddExercise(picked.Selected);

Pick the right moment to load. Every view model gets the same set of moments to hook into. The question to ask is "once, or every time?":

UseWhenGood for
OnInitializedAsyncOnce, the first timeSetting things up
OnTabSelectedAsyncEvery time a tab is openedRefreshing what may have changed elsewhere
OnNavigatedToAsyncEvery time you arrive at a pageSame, for normal pages
OnDisposeWhen the page is goneCleaning up

Wizards are one page with swappable steps. Setup asks four questions. Instead of four pages, it's one host (WizardHostViewModel) and four step views registered with MapView. The host owns the answers and the Back/Next buttons; each step only knows its own question. Nothing is saved until the last step.

Decide what a crash in a screen does. If loading a screen throws, MvvmEssentials can either crash (good while developing) or log and carry on (good for users). It's one setting, plus a hook to send the error to your logger:

opts.LifecycleExceptionBehavior = LifecycleExceptionBehavior.LogOnly;

8. Write the rules down, then check them

Layers stop the worst mistakes, but not all of them. Inside the logbook, "Home may use Workout and Templates, but Exercises uses nothing else" is something the compiler can't see.

So the rules live in a plain table in the docs, one row per feature: what it's for and what it may use. A small tool reads the code, finds which feature uses which, and lists anything that breaks a rule. It sounds like a lot, but because the code is organized by feature folders (point 3), finding "who uses whom" is mostly just reading folder names.

Cheat sheet

  • Register every screen in one place, grouped with comments.
  • Stack your projects in layers. Only the top one knows about MAUI.
  • Put view models in plain libraries so tests run anywhere.
  • Organize folders by feature, not by kind of file.
  • When a lower layer needs something from a higher one, give it a plug (an interface) and let the higher layer fill it.
  • Split busy screens into sections. Let them live and die with their page.
  • Load everything first, then show everything at once.
  • Use typed parameters and popups that return answers.

None of this is clever on its own. It's mostly about making the easy thing and the right thing the same thing. MvvmEssentials is on GitHub and NuGet as Nkraft.MvvmEssentials.
